# Atomic CAS (Compare-And-Swap) API Implementation Plan

**Date**: 2026-03-21
**Target**: `dbx-core` v0.1.2-beta / v0.2.0

## 1. 개요 (Overview)

분산 환경(Grid) 및 단일 노드 다중 스레드 환경에서 데이터 무결성을 보장하기 위해 Atomic CAS(Compare-And-Swap) 연산을 도입합니다. 기존의 `get()` 후 확인하고 `insert()`하는 방식은 Race Condition에 취약합니다.

## 2. 목표 API (Target API)

`Database` 및 내부 `TableStore` 구조체에 다음 4가지 메서드를 추가합니다:

```rust
// 1. 키가 없을 때만 삽입 (성공 시 true, 이미 존재하면 false 반환)
pub fn insert_if_not_exists(&self, table: &str, key: &[u8], value: &[u8]) -> DbxResult<bool>;

// 2. 현재 값이 expected와 일치할 때만 교체 (성공 시 true, 불일치 시 false 반환)
pub fn compare_and_swap(&self, table: &str, key: &[u8], expected: &[u8], new_value: &[u8]) -> DbxResult<bool>;

// 3. 키가 존재할 때만 수정 (성공 시 true, 없으면 false 반환)
pub fn update_if_exists(&self, table: &str, key: &[u8], value: &[u8]) -> DbxResult<bool>;

// 4. 현재 값이 expected와 일치할 때만 삭제 (성공 시 true, 불일치 시 false 반환)
pub fn delete_if_equals(&self, table: &str, key: &[u8], expected: &[u8]) -> DbxResult<bool>;
```

## 3. 구현 세부 계획 (Implementation Details)

### 3.1. 로컬(Local) CAS 구현 (`DashMap` 활용)

현재 DBX의 Delta Store는 `dashmap::DashMap`을 사용합니다. `DashMap`의 `entry()` API를 사용하여 레코드 레벨의 Lock을 잡고 원자적으로 연산을 수행할 수 있습니다.

-   **접근 파일**: `src/engine/crud.rs`
-   **구현 로직**:
    ```rust
    // 예시: insert_if_not_exists
    pub fn insert_if_not_exists(&self, table: &str, key: &[u8], value: &[u8]) -> DbxResult<bool> {
        let store = self.get_table_store(table)?;
        // ... (WOS/Index 체킹 로직 필요) ...
        
        let delta = store.delta_store.read().unwrap();
        use dashmap::mapref::entry::Entry;
        
        match delta.entry(key.to_vec()) {
            Entry::Vacant(v) => {
                // 추가 검증 (Secondary Tier - WOS, Cache 등에 존재하는지)
                // 완벽한 CAS를 위해서는 현재 Delta뿐만 아니라 모든 계층을 확인해야 함.
                // 이를 효율적으로 처리하기 위한 Read-Modify-Write 락 메커니즘 설계 필요.
            },
            Entry::Occupied(_) => return Ok(false), // 이미 Delta에 존재
        }
    }
    ```

### 3.2 핵심 과제: Multi-Tier Storage에서의 동시성 보장

단순히 `DashMap`의 `entry()`만 쓰면 Delta Store 내의 동시성은 제어되지만, WOS(Write-Optimized Store)나 Cache, ROS에 존재하는 과거 버전과의 충돌을 방지해야 합니다.

**해결 방안 (Row-level Latch / Mutex)**:
가장 안전한 방법은 키별로 짧은 시간(Latch) Lock을 획득하는 구조입니다.
1.  CAS 연산 시작
2.  Key에 대한 Row Latch 획득 (예: `scc::HashMap` 기반의 키 단위 락)
3.  Multi-Tier 전체에 대해 조건 검사 (get)
4.  조건 만족 시 Delta에 쓰기
5.  Row Latch 해제

### 3.3. 향후 Grid 확장을 고려한 설계

로컬에서의 Row Latch 메커니즘은 향후 Grid 2PC(Two-Phase Commit)의 Lock Manager로 전환될 수 있습니다. (Prepare 단계에서 이 Latch를 획득).

## 4. 진행 단계별 체크리스트 (Checklist)

1.  [ ] `dbx-core/src/engine/crud.rs`에 CAS API 껍데기(Prototype) 작성.
2.  [ ] Multi-tier를 아우르는 안전한 동시성 제어 도구(Row Latch Lock Manager 등) 설계.
3.  [ ] `insert_if_not_exists` 구현 및 멀티스레드 Race Condition 방지 테스트.
4.  [ ] `compare_and_swap` 구현 및 테스트.
5.  [ ] `update_if_exists`, `delete_if_equals` 구현 및 테스트.
6.  [ ] 성능 벤치마크 (일반 CRUD 대비 CAS 연산의 오버헤드 측정).
