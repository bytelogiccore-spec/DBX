# Network-Aware Lock Manager (DLM) 

**Date**: 2026-03-21
**Target**: `dbx-core` v0.1.2-beta / v0.2.0

## 1. 개요 (Overview)

DBX의 5-Tier Hybrid Storage 아키텍처는 단일 노드에서의 최고 시속을 자랑하지만, 여러 노드가 클러스터링된 분산(Grid) 환경에서도 원자적인 데이터 연산(CAS 등)을 보장해야 합니다.
이를 위해 **분산 락 매니저(Distributed Lock Manager, DLM)**를 도입하여 노드 간의 동시 자원 접근을 정밀하게 제어합니다. 단, 기존 `RowLockManager` 의 초격차 로컬 성능을 보존하기 위해 **분리형 스위칭 구조(Explicit Separation Mode)**를 채택했습니다.

## 2. 핵심 아키텍처 (Core Architecture)

### 2.1 단일 멀티플렉싱 전송 계층 (GridRouter)
기존의 복제용 네트워크 포트를 그대로 유지하되, 내부에서 `GridMessage` 컨테이너를 사용하여 **Replication(복제)** 트래픽과 **Lock(분산 락)** 트래픽을 다중화(Multiplexing)합니다.
- `GridRouter` 컴포넌트가 네트워크 최전방에 위치하여 Inbound/Outbound 채널을 분리.
- 루프 방지(Loop-less) 설계를 통해 기존 복제 노드 소스의 변경 없이 플러그인 형태로 락 시스템을 안착시켰습니다.

### 2.2 Fencing Token 및 Lease 기반 동시성 제어
- **Lease**: 모든 락은 무한정 소유할 수 없으며, 일정 시간의 대여 기한(ex: 5000ms)을 가집니다.
- **Heartbeat 갱신**: 네트워크 단절이 발생하지 않고 연산이 길어질 경우, `Heartbeat` 방출을 통해 코디네이터 노드에 기한 연장을 요청합니다.
- **Passive Eviction (수동 탈취)**: 락을 선점한 노드가 크래시되어 갱신하지 못한 경우, 새로운 노드의 `Acquire` 요청 시 시간을 검증(`now > expiration`)하여 기존 락을 강제로 빼앗아 줍니다(Deadlock 방어).
- **Fencing Token**: 매 락 획득/탈취마다 순차적으로 증가하는 토큰을 발급하여 스토리지 엔진 단에서 구버전 락 보유자의 쓰기 지연(Zombie Write)을 차단할 수 있는 기반을 마련했습니다.

## 3. 분리형 수동 래퍼 (GridDatabaseAsync)

단순 CRUD나 로컬 전용 인메모리 사용 시 성능 오버헤드를 원천 차단(0%)하기 위해, DLM은 철저히 별도의 비동기 래퍼로 제공됩니다. (`src/engine/async_api.rs`)

```rust
// [예시] 분산 환경에서의 원자적 교체 (CAS)
pub async fn compare_and_swap_with_lock(...) -> DbxResult<bool> {
    // 1. 네크워크 코디네이터 노드에 락(Fencing Token) 요청 및 대기
    let fencing_token = self.dlm.acquire(table, key, 5000, timeout).await?;

    // 2. 가장 빠른 로컬 스트라이핑 락을 활용하여 실제 데이터 I/O (HTAP 성능 100% 활용)
    let result = spawn_blocking(|| db.compare_and_swap(...)).await?;

    // 3. 작업 종료 후 사용한 분산 락 즉시 반환
    self.dlm.release(table, key, fencing_token).await;

    result
}
```
